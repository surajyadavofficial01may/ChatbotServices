# RAG Benchmark — Baseline

> **Context:** engineering notes from this project's first deployment, a single-person portfolio assistant (the owner is called "Alex" here). That corpus and its labels are private and not shipped; the shipped benchmark (`python -m benchmarks.evaluate`) runs on `data/sample_entries.json`. Re-run on that private corpus, the current generic pipeline reproduces the final production numbers in [rag-improvement-roadmap.md](rag-improvement-roadmap.md) exactly.

Measured on the **original pipeline, before any change**, so later numbers have
something honest to compare against. Raw output was kept with the private corpus (not shipped).

## Dataset

- **Corpus** — a private, frozen snapshot of the 35 live records
  from Supabase, so old and new pipelines are
  measured on identical data. Refresh it deliberately when the content changes a lot.
  It contains the same public contact details the chatbot is built to share.
- **Cases** — 51 hand-labelled queries (private, alongside the corpus). Every
  `relevant_ids` entry was checked by reading the records, not generated by a model.

| Type | Cases | What it probes |
|---|---|---|
| exact | 16 | names / identifiers / numbers ("What is Tidewatch?", "CGPA?") |
| semantic | 15 | paraphrase and synonyms ("Where did Alex study?") |
| list | 5 | "list all X" — answer spans every record of a category |
| multi | 3 | answer spans several categories |
| typo | 3 | misspellings ("tidewatch monitr") |
| followup | 3 | needs earlier turns ("the first one", "there") |
| negative | 6 | not in the knowledge base, incl. one prompt injection |

## Metrics

Retrieval (binary relevance, on the sources actually handed to the LLM):
Hit@5, Recall@5, Recall@10, Precision@5, MRR, nDCG@5; for negatives the
**abstention rate** (no source passes the evidence gate) and for positives the
**false-rejection rate**.

Generation (27-case subset, live LLM — sized for Groq's free tier of 8k tokens/min):
- **negative refusal rate** — negatives answered with "not available";
- **false refusal rate** — positives refused;
- **fact recall** — hand-picked facts (`must_include`) present in the answer;
- **source precision** — share of returned sources that are actually relevant;
- **citation coverage** — positive answers that cite at least one source.

These are deterministic, not LLM-as-judge. RAGAS/DeepEval were not used: both add
heavy dependencies and spend an LLM call per metric per case, which the 8k
tokens/minute budget can't absorb, and a judge model adds its own noise.

## Baseline configuration

`BAAI/bge-small-en-v1.5`; only `content` embedded (title and category ignored);
raw query embedded (fastembed 0.5.1 adds no instruction prefix); dense cosine
top-5 with a 0.45 floor; context concatenated into a single user message; Groq
default temperature; no conversation support.

## What the baseline exposed

- **"What projects has Alex worked on?" retrieved none of the 8 project records.**
  Only `content` was embedded, and project descriptions don't contain the word
  "project"; bios and skills ranked higher.
- **The 0.45 cosine floor never rejected anything.** Every record names Alex, so
  "What is Alex's favorite movie?" scores 0.59 and "date of birth" 0.70 —
  higher than real answers such as Tidewatch (0.62). The threshold gave no protection.
- **Rare identifiers fail in dense-only search:** "What is Tidewatch?" missed the
  only record mentioning it, so the bot refused an answerable question.
- **Follow-ups fail:** with no history, "What tech stack was used for the first one?"
  retrieved nothing relevant and was refused.
- **70% of returned sources were irrelevant** — all five retrieved records were
  returned regardless of whether the answer used them.
- What already worked: the old prompt's "say it's not available" rule refused all
  six off-topic questions at the generation step, even though retrieval passed
  them through.

Generation scores were recomputed with the final metric functions (facts matched
whitespace-insensitively; refusals include explicit declines), so they compare
like-for-like with the optimised run.

## Reproduce

```powershell
python -m benchmarks.evaluate --configs baseline   # retrieval, offline
```

The `baseline` config re-creates the original behaviour on the new code
(content-only text, no prefix, dense-only, 0.45 floor) and reproduces every
number above exactly, which is how the harness itself was validated.
